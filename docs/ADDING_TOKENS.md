# Adding a New SAC Token to the Asset Whitelist

This guide explains the due diligence process an admin must complete before whitelisting a new Stellar Asset Contract (SAC) token on SoroStream. A hasty or unverified whitelisting can expose streams to non-standard token behaviour, missing liquidity, or outright fraud — so every step below is mandatory.

---

## What Is a SAC Token?

A Stellar Asset Contract (SAC) is the canonical Soroban smart contract that wraps a classic Stellar asset (e.g. USDC, XLM, AQUA) for use by Soroban contracts. SAC tokens are automatically generated by the Stellar protocol and implement the standard `sep-0041` token interface (`transfer`, `balance`, `allowance`, etc.).

**SAC tokens are distinct from custom ERC-20-style token contracts.** SoroStream only accepts SAC tokens because:

1. Their `transfer` semantics are guaranteed by the Stellar protocol — there are no fee-on-transfer hooks, rebasing mechanics, or custom transfer logic.
2. Balance accounting inside SoroStream's vesting math relies on exact `i128` arithmetic that can be invalidated by fee-on-transfer or rebasing tokens.
3. SAC tokens cannot be upgraded or paused by a third-party developer, removing the risk of a rug-pull at the token contract level.

---

## Step 1 — Confirm the Asset Exists on Stellar

Before doing anything on-chain, verify the classic Stellar asset is real and well-established.

1. Look up the issuer account on the [Stellar Expert](https://stellar.expert/explorer/public) block explorer.
2. Confirm the issuer's home domain matches the project's canonical domain (check the `home_domain` field on the issuer account).
3. Check that the asset has been listed for at least 90 days and has a non-trivial number of trustline holders (>100 is a reasonable minimum).
4. Verify the issuer has published a `stellar.toml` file at `https://<home_domain>/.well-known/stellar.toml` that includes a `[[CURRENCIES]]` entry for the asset.

---

## Step 2 — Derive the SAC Contract Address

Each classic Stellar asset has exactly one canonical SAC address derived deterministically from its asset code and issuer.

```bash
# Replace ASSET_CODE and ISSUER_ADDRESS with the actual values.
stellar contract id asset \
  --asset ASSET_CODE:ISSUER_ADDRESS \
  --network mainnet
```

**Example — USDC issued by Centre:**
```bash
stellar contract id asset \
  --asset USDC:GA5ZSEJYB37JRC5AVCIA5MOP4RHTM335X2KGX3IHOJAPP5RE34K4KZVN \
  --network mainnet
```

Save the output address as `$SAC_ADDRESS`. This is the address you will whitelist.

---

## Step 3 — Verify It Is a Genuine SAC

Retrieve the contract's WASM hash and compare it to the known SAC WASM hash published by Stellar.

```bash
# Fetch the contract's WASM hash
stellar contract info \
  --id $SAC_ADDRESS \
  --network mainnet
```

The `wasm_hash` field in the output must match the canonical SAC WASM hash for the current protocol version. Canonical WASM hashes are published in the [Stellar Protocol Upgrade Notes](https://github.com/stellar/stellar-protocol/blob/master/core/cap-0046-12.md) and on the [Stellar Expert contract page](https://stellar.expert/explorer/public/contract/$SAC_ADDRESS).

> **Red flag:** If the WASM hash does not match a known SAC hash, the contract is a custom token contract masquerading as a SAC. Do not whitelist it.

Optionally, call the `symbol` and `decimals` read functions to sanity-check the metadata:

```bash
stellar contract invoke \
  --id $SAC_ADDRESS \
  --network mainnet \
  -- symbol

stellar contract invoke \
  --id $SAC_ADDRESS \
  --network mainnet \
  -- decimals
```

Confirm the symbol and decimals match the `stellar.toml` entry found in Step 1.

---

## Step 4 — Confirm Sufficient Liquidity

SoroStream streams lock tokens for potentially long durations. Low-liquidity tokens create problems for senders who need to acquire tokens for top-ups or renewals.

Check the following on [Stellar Expert](https://stellar.expert/) or [StellarX](https://www.stellarx.com/):

| Signal | Minimum Threshold |
|--------|-------------------|
| Trustline holders | ≥ 100 |
| 30-day trading volume | ≥ $10,000 equivalent |
| Order book depth (1% slippage) | ≥ $5,000 |
| DEX liquidity pools | At least one active pool |

If the token fails these thresholds, note the risk in the whitelist proposal and consider deferring until liquidity is established.

---

## Step 5 — Due Diligence Checklist

Complete every item before submitting the whitelist transaction. This checklist should be copy-pasted into the governance proposal or admin action record.

```
SAC Token Whitelist Checklist
==============================
Token:       <ASSET_CODE:ISSUER>
SAC Address: <$SAC_ADDRESS>
Date:        <YYYY-MM-DD>
Reviewed by: <admin address>

[ ] Classic Stellar asset exists and issuer home_domain is verified
[ ] stellar.toml published at issuer home_domain and includes this asset
[ ] Asset has been live for ≥ 90 days
[ ] Trustline holders ≥ 100
[ ] SAC address derived via `stellar contract id asset` and matches on-chain contract
[ ] WASM hash matches canonical SAC WASM hash for current protocol version
[ ] symbol() and decimals() return values match stellar.toml metadata
[ ] 30-day trading volume ≥ $10,000 equivalent
[ ] DEX order book depth sufficient (≥ $5,000 at 1% slippage)
[ ] No known security incidents or issuer controversies
[ ] Protocol team consensus reached (if multi-sig governance is active)
```

---

## Step 6 — Whitelist the Token on SoroStream

> **Note:** The SoroStream whitelist controls _recipient_ addresses, not token addresses. The contract accepts any SAC token passed to `create_stream`. The due diligence process above is for off-chain governance — to decide which tokens the protocol _recommends_ and which the frontend allows — and for any future on-chain token gating that may be added. The CLI commands below apply to the recipient whitelist; adapt them if an on-chain token registry is introduced.

Once due diligence is complete, record the token metadata in the protocol's registry (internal spreadsheet, governance forum post, or on-chain registry depending on the current governance setup), then enable streaming for this token in the official frontend configuration.

If recipient whitelisting is enabled and you also want to gate which recipients can receive a new token's streams, use:

```bash
# Enable the whitelist (if not already enabled)
stellar contract invoke \
  --id $CONTRACT_ID \
  --source admin-key \
  --network mainnet \
  -- set_whitelist_enabled \
  --admin $ADMIN_ADDRESS \
  --enabled true

# Add an approved recipient
stellar contract invoke \
  --id $CONTRACT_ID \
  --source admin-key \
  --network mainnet \
  -- add_to_whitelist \
  --admin $ADMIN_ADDRESS \
  --recipient $RECIPIENT_ADDRESS
```

## Security Risks of Whitelisting Non-SAC Tokens

If a non-SAC token contract were ever accepted:

| Risk | Impact |
|------|--------|
| Fee-on-transfer | Contract receives less than `amount`, causing balance shortfalls on withdrawal |
| Rebasing | `balance` calls return stale values, breaking vesting math invariants |
| Upgradeable token | Token issuer can alter `transfer` behaviour mid-stream, stealing funds |
| Pauseable token | Issuer can freeze transfers, locking funds in the stream contract indefinitely |
| Fake symbol/decimals | Frontend displays incorrect amounts, causing user confusion and potential loss |

The formal verification in `vesting_math.rs` (Kani proofs) assumes exact integer arithmetic with no side effects on token transfers. Any deviation from standard SAC semantics breaks these invariants.
